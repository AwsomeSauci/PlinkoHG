# Контракты модуля Plinko

Разработчик: **IDDLEX**. Актуализировано **11 сентября 2026**. Текущая архитектура: Passive View MVP, заменяемый игровой сервис, чистый домен и адаптеры. Реализована локальная игра; сервер и сетевой транспорт в проект не добавлены.

## Интерфейсы в Lua

В Lua 5.1 нет ключевого слова `interface` и статической проверки типов. Контракт задаётся именами методов, параметрами, результатами и поведением. Реализация — объект с методами; вызывается через `instance:Method(...)`. Проверка `Ports.Require` при сборке ловит отсутствующие методы. Аннотации `---@class`/`---@field` описывают типы для Lua-инструментов. Поведенческую часть проверяют спецификации.

Объявления: `scripts/contracts/game_service.lua` и `scripts/contracts/ports.lua`. Это структурная типизация: наследоваться от пустого базового класса не требуется. Контейнер DI не используется; зависимости явно передаются конструкторам.

| Контракт | Ответственность | Реализация |
| --- | --- | --- |
| `IGameService` | Команды, авторитетное состояние и события результата | `LocalGameService` |
| `ISessionRepository` | Асинхронная загрузка/запись snapshot из заменяемого источника | `SessionRepository` → `SaveStore` → `DefoldStorage` |
| `IClock` | Экономическое время | `SystemClock` → `os.time` |
| `IGameView` | Пассивный экран, эффекты, визуальные объекты | `GameView` → `Hud`/`BoardView` |
| `IFlightSimulation` | Построение и обновление визуального полёта | `FlightSimulator` → `Board`/`Flight` |

## IGameService: методы

Все методы принадлежат одному экземпляру игры. Presenter владеет этим экземпляром до `Dispose`.

| Метод | Контракт |
| --- | --- |
| `Open()` | Начать загрузку. Повтор не создаёт ещё одну сессию. Результат может появиться через несколько кадров. |
| `Execute(command)` | Передать намерение. Возвращает ID команды, **не подтверждение успеха**. Статус приходит событием `CommandStatus`. Вне ready возвращает nil и не принимает команду. |
| `Landed(dropId)` | Сообщить об окончании изображения полёта. Это не доказательство права на награду. |
| `Update(dt)` | Обработать время, завершённые операции и повторы. `dt` конечный, неотрицательный, в секундах. |
| `GetState(includeDetails)` | Вернуть отделённую от внутреннего состояния проекцию. Без I/O, начислений и продвижения часов. |
| `DrainEvents()` | Забрать очередь событий по порядку; второй вызов без новой работы возвращает пустой массив. |
| `Suspend()` | Обработать потерю фокуса/приостановку. Для локального варианта — checkpoint. |
| `Resume()` | Обновить состояние после возврата. Для локального варианта — офлайн-восстановление и checkpoint. |
| `Flush(completed)` | Подтвердить запись изменений до этого вызова; callback(true) либо callback(false, detail). Может завершиться сразу или позже. |
| `Dispose()` | Завершить владение. Идемпотентен; дальнейшие Update/Execute/Landed не меняют игру и не публикуют события. |

Игровые команды используют очередь событий. Для управляемого закрытия хост может вызвать Presenter.Flush с callback подтверждения. Асинхронная реализация может принимать callback от HTTP, но складывает результаты в свою очередь и публикует их на потоке владельца. Она не вызывает GUI из транспортного callback. После Dispose её отменённые или запоздалые ответы игнорируются.

Plinko.Create принимает владение переданными Service/View. Если последующая сборка Presenter не удалась, обе реализации получают Dispose. Presenter.Dispose пытается отменить ввод, освободить сервис, каждый шар и View независимо; накопленные ошибки возвращаются после всех попыток. Повторный Dispose безопасен. Defold host логирует ошибки очистки и продолжает освобождение input focus. Успешное освобождение внешнего ресурса при ошибке его собственного Dispose гарантировать нельзя; гарантируется вызов остальных независимых стадий.

Ошибки хранения/связи — данные состояния и событий. Отсутствующий метод, некорректный программный вызов или нарушение протокола разработчиком — ошибка контракта. Метод не должен бросать исключение при обычном сетевом отказе.

### Команды

```lua
service:Execute({Kind = "Drop", Count = 5})
service:Execute({Kind = "Grant"})
```

Drop сообщает только количество. Presenter не передаёт выбранную корзину, сумму выплаты, RNG или время начисления. Grant — существующая debug-команда задания; будущий backend должен отдельно разрешать её или возвращать отказ. Клиентский доступ к кнопке не является авторизацией.

Presenter не повторяет Execute по таймеру. Сервис отвечает за корреляцию запросов, дедупликацию, порядок принятия ответов и безопасный повтор. Каждый Execute означает новое намерение и получает новый ID в пределах экземпляра сервиса; повторять Execute после Pending нельзя. В локальной реализации команда меняет состояние в памяти сразу, а запись повторяется в SessionPersistence, а выдача — в Game без повторного выбора исхода. ID возвращается вызывающему коду и присутствует в каждом CommandStatus. Будущий сервис сопоставляет этот ID со стабильным серверным ключом идемпотентности; локальные ID не обещают корреляцию между перезапусками.

### Состояние

```lua
{
    Phase = "ready", -- new / opening / ready / failed / disposed
    Busy = false,    -- ожидается подтверждение; новые команды временно закрыты
    Error = nil,     -- диагностика текущего отказа или ожидания retry
    Model = {
        Balls = 11, Score = 0, ActiveCount = 1,
        TotalHits = 0, SettledCount = 0, ArchivedHits = 0,
        InFlightCount = 1, PendingRewardCount = 0,
        RefillRemaining = 30, RefillProgress = 0,
        SavingBlocked = false, SavingPending = false, RewardBlocked = false,
        -- При includeDetails=true:
        Hits = {}, RewardState = {},
    },
}
```

Это схема формы, не готовый snapshot: массив Hits и RewardState в настоящем ответе содержат текущие данные. Hits: `Id`, `Count`, `Percent`, `WeightPercent`, `Rewards`; порядок совпадает с Config.Baskets. RewardState: пространства `{Version, Data}` зарегистрированных типов. До Ready Model может отсутствовать. После Ready для обычного обновления требуется Model, а при запросе подробностей — заполненные Hits/RewardState. UI может удержать последнюю картинку при терминальном отказе, но не считает её актуальным балансом.

Busy не ограничивает количество летящих шаров. Это состояние ожидания сервиса. LocalGameService возвращает Busy=true во время загрузки и любой записи, в том числе фоновой. SavingPending отражает незавершённую операцию записи в Model. SavingBlocked отдельно показывает отказ сохранения, в том числе при запуске или записи выплат. Pending означает, что действие принято в память, но его долговечность ещё не подтверждена. Подтверждённые полёты продолжаются, пока сервис ждёт новый ответ; новый исход на клиенте не угадывается.

Конфигурация приходит один раз через Ready. Для этого экранного lifetime она стабильна. Обновление доски с другой конфигурацией оформляется новым экземпляром Presenter/View/Service. Восстановление при правке локального конфига остаётся обязанностью Session.

### События

| Kind | Payload и смысл |
| --- | --- |
| `Ready` | `Config`: сериализуемые данные для отображения и построения поля. Публикуется один раз и раньше Started/Awarded. GetState уже доступен. |
| `Started` | `Drop = {Id, BasketId, BasketIndex, Seed}`: подтверждённый исход для анимации, без вычисления наград в Presenter. |
| `Awarded` | `Drop` с теми же идентификаторами и полным `Rewards`: состоявшаяся выдача. |
| `CommandStatus` | `Id`, `Command`, `Status`: Pending / Succeeded / Rejected; опционально Code и Amount. Pending не терминален. Succeeded подтверждает checkpoint команды. Rejected не оставляет принятых списаний/выдач. Amount сохраняется для отложенного Grant. |
| `Notice` | `Code`, опционально `Amount`/`Detail`: восстановление или другая известная информация. |
| `SaveFailed` | `Detail`: диагностика локальной записи; игровая причина — SaveError. |
| `RewardFailed` | `Detail`: пакет остался ожидающим. Presenter не повторяет его самостоятельно. |

Id является стабильным скалярным идентификатором: локально это целое число, другая реализация может использовать строку. BasketIndex — целое 1..N для Started; удалённая корзина может иметь 0 в Awarded без анимации. Seed — конечное целое для воспроизводимого визуального маршрута. BasketId соответствует конфигурации Ready. Наборы Rewards соответствуют formatter-ам, предоставленным хостом.

Сервис публикует каждый Started/Awarded один раз в своём lifetime; повторная доставка транспортного ответа не должна превращаться в новое UI-событие. При восстановлении нового экземпляра прежний незавершённый исход может снова получить Started. Presenter дополнительно не создаёт второй visual для уже активного ID, но не хранит бесконечную историю всех событий.

Если авторитетная награда получена до окончания полёта, Presenter задерживает только эффект корзины до его завершения. Баланс из сервиса не откатывается и не высчитывается повторно. Если ответ приходит после полёта, visual уже освобождён, а событие отображается при получении.

Команда получает не более одного терминального статуса. В локальной реализации это сразу Rejected/Succeeded либо Pending → Succeeded после восстановления записи. Будущий сетевой сервис может завершить ожидание Rejected, если авторитетно установлено, что действие не принято и никаких оставшихся списаний/выдач нет; один timeout этого не доказывает. При повторных сбоях Pending не спамится; сервис остаётся Busy. Новое намерение во время ожидания получает собственный ID и Rejected(busy), не меняя принятую команду. Постоянная ошибка repository или конфликт переводит сервис в failed; результат принятой неподтверждённой команды не объявляется отказом, а требует восстановления из источника. Гарантия доставки действует пока экземпляр работоспособен и события читаются: Dispose прекращает её, делает последнюю попытку записи накопленных изменений и очищает очередь. Для управляемого закрытия нужно дождаться Flush; Dispose не ждёт сеть. Неподтверждённое изменение в памяти может потеряться при аварийном закрытии; это не равно отказу команды. После перезапуска состояние восстанавливается из последнего согласованного checkpoint, без переиздания старых статусов UI.

TotalHits — все зафиксированные попадания, независимо от успеха награды. SettledCount — число полностью выданных пакетов, не количество отдельных предметов. PendingRewardCount — приземлившиеся, но ещё не выплаченные броски; InFlightCount — ещё не приземлившиеся. ActiveCount — их сумма.

Коды отказа команд: `insufficient_balls`, `save_failed`, `busy`, `unavailable`, `session_limit`, `invalid_count`, `invalid_command`. Pending при записи имеет Code=save_pending. Неизвестная ошибка отображается как недоступность, а её перевод в эти причины выполняет адаптер сервиса.

## Остальные порты

`ISessionRepository:Load(request, completed)` и `Save(request, completed)` — асинхронные методы, допускающие мгновенный ответ. В запросе находятся Id, а для Save также Snapshot и ExpectedRevision. Callback получает Status=ok/retry/failed/conflict; успешный результат содержит Revision, успешная загрузка — Snapshot (nil только для отсутствующего сохранения). Dispose отменяет владение ресурсами. Полная схема, retry, условия идемпотентности, версии, Flush и пример подключения: [PERSISTENCE_CONTRACT.md](PERSISTENCE_CONTRACT.md).

Передача `options.Repository` заменяет только источник сохранений; LocalGameService и доменные расчёты остаются прежними. Передача `options.Service` заменяет всю авторитетную игровую логику. Это две независимые границы расширения.

`ISaveBackend` — низкоуровневый локальный адаптер: Path(namespace, filename), Read(path), Write(path, envelope), все через двоеточие. Read возвращает {Status="missing"}, {Status="loaded", Value=...}, {Status="corrupt", Error=...} или {Status="unavailable", Error=...}. Исключение Read трактуется как unavailable. Только явный missing допускает новую игру; corrupt допускает проверенный резервный слот; unavailable запрещает запись обоих слотов. Write подтверждает успех только true. Передавать сырой sys вместо адаптера нельзя.

`IClock:Now()` возвращает абсолютное экономическое время в секундах. Presenter его не знает. Симуляция использует только dt; локальное накопление запасов — часы сервиса. Другой сервис может полностью опираться на серверное время.

`IFlightSimulation:Configure(count)` задаёт геометрию, `Create(descriptor)` создаёт полёт, `Update(flight, dt)` изменяет X/Y/Done и возвращает пересечённые кегли. Полёт сохраняет Id и BasketIndex. Симуляция не выбирает награды. Замена этой реализации не требует изменения сервиса экономики.

`IGameView` принимает Configure(config, initialModel), Render(state, dt), Notify, SetStats, SetMuted, PlaySound, AddBall/MoveBall/RemoveBall, Contact, Award, CancelInput, Dispose. Аннотации содержат точные параметры. View не получает сервис и не вызывает доменные методы. Декор, форматирование, размеры и hit testing принадлежат View. Pointer — дополнительный метод конкретного Defold GameView, который возвращает строковое намерение в engine adapter.

## Замена локальных расчётов сервисом с backend

В `Plinko.Create(parent, options)` передаётся готовый экземпляр `options.Service`. При его наличии код не создаёт LocalGameService, Registry, SessionRepository и SystemClock и не валидирует локальный config/game.lua. Presenter, FlightSimulator, HUD и обработка ввода остаются теми же.

```lua
local presenter, view = Plinko.Create(gui.get_node("root"), {
    Service = host.PlinkoService,
    RewardTypes = host.PlinkoRewardViews,
})
Presenter.Start(presenter)
```

`host.PlinkoService` здесь — зависимость из игры-хоста, реализующая описанный контракт, а не существующий сетевой класс этого репозитория. RewardTypes для такого варианта может содержать только Type/View: локальные Handler не нужны. Транспорт, адреса, токены, DTO backend и преобразование ответа находятся внутри будущего сервиса и его infrastructure-адаптеров.

Будущий backend обязан сам выбирать исход и проверять запас/награды. Для неясного результата после timeout нужны стабильные идентификаторы команд, проверка их статуса и идемпотентность на стороне backend. Повтор HTTP-запроса с новым ID может повторно списать запас; Presenter этого исправить не может. Серверная выдача не должна зависеть от доверия к клиентскому Landed. Сервер должен сам завершать/восстанавливать принятые операции, даже если игрок закрыл клиент.

Здесь подготовлена граница замены и проверено её поведение без синхронного результата. Реальный транспорт, серверное хранилище, авторизация и распределённые гарантии потребуют реализации конкретного backend. Они не появляются от объявления интерфейса.

## Встраивание и владение

Для сохранения локальной логики можно передать Config, RewardTypes, Repository или Storage/StorageNamespace, Clock, Simulation, View. Все зависимости создаются для экземпляра; глобального service locator нет. Параметры UI/звука движка не попадают в домен.

Хост вызывает Start один раз, Update(dt), Activate(intent), SetFocus(bool), при управляемом закрытии Flush(completed), затем Dispose. Он сам маршрутизирует события своего окна и ввод. `main.gui_script` — готовый адаптер для самостоятельного запуска задания; при встраивании не нужно устанавливать второй глобальный window listener.

Для нескольких локальных игр нужны разные StorageNamespace или независимые Repository. Для нескольких Defold-досок нужны отдельные mesh-компоненты и buffer resources. Их можно передать через `options.Render = {MeshUrl = ..., BufferResource = ...}`. Один общий buffer resource по-прежнему означает общие вершины. Хост также подключает материалы/predicate рендера, GUI-шрифты и sound-компоненты либо предоставляет собственный IGameView.

Спецификации `tests/mvp_spec.lua` проверяют независимые экземпляры, локальный путь с настоящим Flight, отказ загрузки/сохранения, чистоту проекции, ожидание команды, поздний/ранний результат, lifecycle и обход локальных зависимостей при переданном сервисе. В production-коде имеется одна реализация IGameService — LocalGameService.
