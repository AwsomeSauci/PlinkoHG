# Конфигурируемые награды

У корзины есть список `Rewards`, а не поле `Points`. Одна запись может выдавать очки, шары, предмет или новый зарегистрированный тип. Исходный конфиг сохраняет прежние points-награды из ТЗ; примеры ниже включают дополнительные возможности вручную.

```lua
{ Id = "supplies", Weight = 3, Color = "B9C47F",
  Rewards = {
      {Type = "points", Amount = 100},
      {Type = "balls", Amount = 2},
      {Type = "item", ItemId = "leaf", Name = "Лист", Amount = 3},
  },
},
```

`config/game.lua` задаёт баланс. `config/reward_types.lua` связывает Type с доменным Handler и отдельным View. Вызов `Registry.New` проверяет контракт; `Config.Validate` нормализует определения. `RewardText` проверяет доступные formatter перед созданием сцены. Зависимость от registry передаётся в валидированную runtime-конфигурацию явно; реестр не входит в snapshot.

## Контракт и владение данными

| Член Handler | Контракт |
| --- | --- |
| `Version` | Положительное целое. Версия данных и их смысла, включая состояние типа. |
| `Normalize(definition, context)` | Каноническая таблица или `nil, error`. Registry сам добавляет `Type` и `Version`. |
| `NewState(context)` | Новая таблица состояния этого типа. Не хранить изменяемое состояние в самом модуле. |
| `ValidateState(data, context)` | Проверенная таблица или `nil, error`. Вызывается после загрузки и после применения всего пакета. |
| `Apply(draft, reward, context)` | Меняет только переданный draft. Возвращает `true` или `false, error`. |
| `ValidateBundle(rewards, context)` | Необязательная проверка целого набора одного типа в конфиге. Например, сумма ball-наград должна помещаться в MaxInventory. |
| `RequiredState` | Необязательный флаг: отсутствие состояния в snapshot считается ошибкой. Встроенные points/balls обязательны. |

`context` содержит копию `InitialBalls`, `MaxInventory`, `Saved`. `Saved=true` означает проверку уже обещанной награды; изменение лимита не должно незаметно менять её количество. Для собственных настроек можно создать handler фабрикой с явно переданным каталогом и замкнуть его в функциях регистрации. Context не является service locator.

Переданные определения копируются; живую Session обработчик не получает. Данные — конечные числа, строки, boolean и обычные таблицы без циклов, metatable, функций и userdata; глубина меньше 16. Набор корзины — плотный массив из 1–32 записей. Встроенные Amount ограничены 1 000 000, points допускает 0. Это проверяемые границы формата, не лимит одновременно летящих шаров.

Registry применяет награды в порядке списка. Повторные записи одного типа складываются в одном draft. `item` хранит Counts по стабильному ItemId и Names для отображения; последнее успешное начисление задаёт название этого ID. Поэтому используйте одно имя одного предмета в конфиге. Имя не определяет идентичность предмета.

## Атомарность и повторная выдача

`Session.Drop` фиксирует выбранную корзину, seed и независимую копию полного Rewards. Game подготавливает checkpoint со списанием и pending; LocalGameService отправляет его через SessionPersistence в ISessionRepository. Только подтверждение этого checkpoint позволяет Game выпустить событие Started. Анимация получает только ID, корзину и seed.

`Registry.Apply` копирует затронутые пространства состояния, выполняет Apply и повторную ValidateState. Только полный успех заменяет `RewardState`, закрывает pending ID и увеличивает SettledCount. Попадание уже зафиксировано отдельным Session.Land и не откатывается при отказе награды. Отказ, исключение или несериализуемый результат любого handler отменяет изменения всего набора. Автовосстановление — отдельное правило времени, не часть выдаваемого пакета.

Game освобождает необходимость держать Flight ради повторной выплаты: Presenter удаляет visual после приземления, а приложение повторяет отклонённую выдачу раз в секунду. Новые броски позволяют освободить место для ball-награды. Ошибка кода требует исправления handler; ожидание не гарантирует, что произвольная ошибка исчезнет сама.

Например: запас после списания 18, MaxInventory=20, награда — 100 очков + 5 шаров. Ничего не выплачено, pending сохранён. После расходования трёх шаров повтор начисляет весь пакет: запас 20 и счёт +100. Если MaxInventory уменьшен ниже прежнего обещанного Amount, его нужно увеличить обратно; сохранённое право на выдачу не удаляется.

Это транзакция **состояния в памяти**. Запись в два файла обеспечивает восстановление checkpoint, но не ACID или гарантированный fsync. Внутри handler запрещены HTTP, звук, сообщения движку, platform achievements и другие внешние побочные эффекты: после аварийного завершения может повториться выдача из прежнего pending. Для внешних действий требуется отдельный протокол идемпотентности/подтверждений, а не новый локальный Apply.

## Состояние и версии

```lua
RewardState = {
    points = {Version = 1, Data = {Balance = 100}},
    balls = {Version = 1, Data = {Balance = 13}},
    item = {Version = 1, Data = {
        Counts = {leaf = 3}, Names = {leaf = "Лист"},
    }},
}
```

`Score` и `Balls` для HUD вычисляются из этого состояния; дублирующихся сохранённых балансов нет. Snapshot/envelope используют Version=3 и слоты `session-v3-a/b`. По прямому решению автора предыдущие сохранения (v1/v2) не мигрируются, не читаются и не удаляются.

Версия типа проверяется и в RewardState, и в pending Rewards. Неизвестный тип или версия в любом слоте блокирует запись даже при наличии более старого пригодного слота. Это защищает награды при удалении модуля или запуске другого набора модулей. Новый необязательный тип может инициализировать пустое состояние у существующего игрока. Смена смысла данных требует повышения Version и отдельного решения о преобразовании; незаметно переопределять старые обещания нельзя.

## Пример четвёртого типа: открытие области

Создайте `scripts/domain/rewards/unlock.lua`:

```lua
local Data = require "scripts.domain.rewards.data"
local Unlock = {Version = 1}

function Unlock.Normalize(reward)
    if not Data.Id(reward.Key) then return nil, "Invalid unlock key" end
    return {Key = reward.Key}
end

function Unlock.NewState()
    return {Unlocked = {}}
end

function Unlock.ValidateState(state)
    if type(state) ~= "table" or type(state.Unlocked) ~= "table" then
        return nil, "Invalid unlock state"
    end
    for key, value in pairs(state.Unlocked) do
        if not Data.Id(key) or value ~= true then
            return nil, "Invalid unlock entry"
        end
    end
    return state
end

function Unlock.Apply(state, reward)
    state.Unlocked[reward.Key] = true
    return true
end

return Unlock
```

Создайте `scripts/ui/unlock_view.lua`:

```lua
return {
    Format = function(reward, text)
        return text("RewardUnlock", reward.Key)
    end,
    Balance = function(state, text)
        return state.Unlocked.forest and text("ForestUnlocked") or nil
    end,
}
```

Добавьте соответствующие строки в существующий каталог `strings.lua`, затем запись в `config/reward_types.lua`:

```lua
{Type = "unlock",
 Handler = require "scripts.domain.rewards.unlock",
 View = require "scripts.ui.unlock_view"},
```

Теперь в Rewards можно использовать `{Type="unlock", Key="forest"}` вместе с любыми другими типами. Не нужны изменения `Session.Complete`, `SaveStore`, `BoardView` или `Hud`. В `tests/rewards_spec.lua` такой четвёртый тип уже проверен целиком, с собственным форматом состояния. Пример не добавляет новую игровую область в исходную Plinko: он демонстрирует право/флаг, который могла бы читать другая механика.

## Что остаётся конкретным

Points и Balls — обязательные концепции правил Plinko: общий счёт, цена броска и refill. Registry расширяет выдачу; он не делает произвольную игру из текущей экономики. Новому экрану инвентаря или расходованию предметов потребуются свои сценарии. Для большого контента нынешней однострочной сводки будет мало.

View.Format поддерживает `badge`, `table`, `full`. На тесной корзине составной пакет обозначается количеством наград; подробности находятся в статистике и уведомлении. View.Balance добавляет сводку собственного состояния. Форматирование не меняет бизнес-данные.

Стоимость выдачи зависит от пакета и копируемых состояний: для большого инвентаря предметов она не O(1). За O(1) работает поиск/удаление pending ID. Snapshot обходит все pending и состояния. Эти границы лучше профилировать по реальному контенту, чем скрывать за заявлением об «универсальной» архитектуре.

## Попадание и выдача

Session.Land фиксирует попадание и фазу Landed независимо от Apply. Session.Complete принимает только Landed, атомарно применяет пакет и увеличивает SettledCount. При отказе TotalHits/процент уже отражают попадание, Score и остальные награды не меняются. Сохранение хранит фазу, поэтому после перезапуска ожидающая награда повторяется без нового полёта и без повторного попадания. Для новой корзины и нового типа награды эти правила одинаковы.
